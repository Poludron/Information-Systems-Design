## 1. Цели и предпосылки

---

### 1.1. Зачем идём в разработку продукта?

**Бизнес-цель.** Автоматизировать проверку личности сотрудников на проходных промышленного предприятия с помощью распознавания лица, заменив или дополнив ручной процесс, при котором дежурный визуально сравнивает человека с фотографией в пропуске.

**Целевые эффекты:**
- снижение риска несанкционированного доступа;
- ускорение прохода сотрудников;
- снижение нагрузки на охрану;
- исключение человеческой ошибки и субъективности;
- повышение уровня аудита и контроля доступа;
- возможность отказа от части пластиковых пропусков.

**Почему ML лучше текущего процесса.** Ручная проверка зависит от внимания дежурного, плохо масштабируется на 10 проходных, не даёт объективного журнала решений и уязвима к использованию чужого пропуска. ML-система работает 24/7 с одинаковым качеством, автоматически идентифицирует сотрудника по базе (~5000 человек), проверяет liveness и фиксирует каждое событие.

**Критерий успеха итерации.** Пилот на 1–2 КПП, в котором система корректно распознаёт сотрудников, доля ложных отказов не создаёт очередей, доля ложных допусков близка к нулю, есть журнал событий и понятный fallback-режим для охраны.

---

### 1.2. Бизнес-требования и ограничения

**Бизнес-требования:**
1. Идентификация сотрудника по лицу в режиме 1:N по базе ~5000 человек.
2. Проверка liveness (защита от фото, видео, маски).
3. Интеграция с СКУД и турникетом.
4. Журналирование всех попыток прохода.
5. Ручное подтверждение охраной в спорных ситуациях.
6. Административный интерфейс для регистрации и обновления биометрии.
7. Синхронизация с HR-базой и базой пропусков.
8. Поэтапное масштабирование на 10 проходных.
9. Разграничение прав доступа по подразделениям, сменам, зонам.

**Бизнес-ограничения:**
- биометрические данные — специальная категория персональных данных;
- необходимо соблюдение 152-ФЗ;
- предпочтительна обработка данных в защищённом контуре предприятия;
- недопустимы массовые ложные отказы;
- условия промышленной среды: освещение, пыль, спецодежда, каски, очки, бороды;
- охрана должна иметь возможность мгновенно перейти в ручной режим.

**Ожидания от итерации.** MVP-пилот на 1–2 КПП: регистрация ограниченной группы сотрудников, распознавание лица, базовая проверка liveness, интеграция с одним турникетом, журнал событий, ручной fallback, отчёт по качеству.

**Бизнес-процесс пилота:**
1. Сотрудник подходит к КПП.
2. Камера фиксирует кадр.
3. Система выделяет лицо и рассчитывает эмбеддинг.
4. Выполняется поиск по базе сотрудников.
5. Проверяется liveness.
6. Проверяются права доступа.
7. При подтверждении — турникет открывается.
8. При неуверенности — сигнал охране для ручного решения.
9. Событие записывается в журнал.

**Критерии успешного пилота:**
- FRR ≤ 1–2% в контролируемых условиях;
- FAR ≤ 0,001–0,01% для критичных зон;
- доля пропущенных подделок ≤ 0,1%;
- среднее время прохода ≤ 2 секунды;
- ≥ 95% проходов без вмешательства охраны;
- отсутствие критичных инцидентов безопасности;
- положительная обратная связь от охраны и сотрудников.

**Возможные пути развития:** масштабирование на все 10 КПП, отказ от пластиковых пропусков, интеграция с учётом рабочего времени, мультикамерное сопровождение, защита от несанкционированного прохода группы, мобильная перерегистрация, аналитика потоков, автоматическое переобучение модели.

---

### 1.3. Что входит в скоуп проекта/итерации, что не входит

**Входит в MVP:**
- сбор и подготовка данных;
- модуль регистрации сотрудника (фото, эмбеддинг, привязка к HR-ID);
- модуль распознавания лица 1:N;
- базовая проверка liveness;
- интеграция с 1–2 КПП и турникетом/СКУД;
- журнал событий;
- ручной режим охраны;
- административная панель;
- отчётность по качеству пилота.

**Не входит в MVP:**
- полноценная защита от несанкционированного прохода группы;
- мультикамерное сопровождение по территории;
- продвинутый anti-spoofing для всех типов атак;
- мобильное приложение;
- интеграция со всеми 10 КПП;
- автоматическое переобучение;
- глубокая аналитика перемещений;
- полная замена пропусков.

**Качество кода и воспроизводимость:**
- код в Git-репозитории с понятной структурой;
- конфигурации вынесены отдельно;
- данные и модели версионируются;
- README с инструкцией запуска;
- базовые тесты критичных модулей;
- описание пайплайна обучения и инференса.

**Технический долг:**
- улучшение liveness и anti-spoofing;
- балансировка качества по группам сотрудников;
- автоматический мониторинг дрейфа;
- retraining pipeline;
- оптимизация latency на edge;
- защита от несанкционированного прохода группы;
- интеграция со всеми КПП;
- расширенный аудит и отчётность.

### 1.4. Предпосылки решения

**Общие предпосылки:**
1. Есть HR-база сотрудников и фотографии для пропусков.
2. Возможна дополнительная фотосъёмка для повышения качества базы.
3. На КПП можно установить камеры и вычислительные модули.
4. СКУД или турникеты имеют API для интеграции.
5. Есть или может быть получено согласие сотрудников на обработку биометрии.
6. Возможна обработка данных в защищённом контуре предприятия.
7. Пилот можно провести на ограниченной группе сотрудников и 1–2 КПП.

**Используемые данные:**
- HR-данные (ФИО, табельный номер, подразделение, должность, статус);
- фотографии сотрудников (эталонные и дополнительные ракурсы);
- биометрические эмбеддинги лиц;
- данные СКУД (права, зоны, смены);
- события проходов (время, КПП, камера, результат, уверенность);
- видеопоток с КПП для валидации и liveness.

**Горизонт и гранулярность:**
- online-инференс в момент прохода;
- пересчёт эмбеддингов при регистрации или обновлении фото;
- переобучение модели по мере накопления данных и дрейфа;
- гранулярность — одно событие прохода.

**Распределённый характер данных:**
- видеопоток формируется на edge-устройствах КПП;
- эмбеддинги хранятся в векторной БД;
- метаданные — в реляционной БД;
- фотографии — в объектном хранилище;
- СКУД и HR — внешние системы;
- часть обработки выполняется локально на КПП для низкой задержки и отказоустойчивости.

## 2. Методология

---

### 2.1. Постановка задачи

В рамках проекта решается комплексная задача компьютерного зрения (Computer Vision), объединяющая два взаимосвязанных направления:

1. **Идентификация лица в режиме 1:N** (face identification) — поиск наиболее вероятного сотрудника по базе из ~5000 человек.
   - Входные данные: изображение (кадр) с камеры на проходной.
   - Выходные данные: идентификатор сотрудника, степень схожести (similarity score), итоговое решение «доступ разрешён / запрещён».
   - Класс метрик: FAR, FRR, TAR@FAR, EER, Rank-1.

2. **Проверка живости лица** (liveness detection, anti-spoofing) — определение того, что перед камерой находится реальный человек, а не его фотография, видеозапись, маска или иной способ имитации.
   - Входные данные: изображение или короткая видеопоследовательность.
   - Выходные данные: бинарная классификация «живое лицо / подделка».
   - Класс метрик: APCER, BPCER, ACER.

Дополнительно система решает прикладные задачи: проверка прав доступа (по зоне, смене, времени), интеграция с системой контроля управления доступом (СКУД), журналирование событий, уведомление охраны в спорных ситуациях.

**Формализация.** Пусть задано множество эмбеддингов (embedding — числовое представление лица, вектор фиксированной размерности) эталонных лиц сотрудников \( E = \{e_1, ..., e_N\} \), где \( N \approx 5000 \). Для кадра с камеры вычисляется эмбеддинг \( x \). Решение о допуске принимается при одновременном выполнении условий:

- \( \max_i \ \text{sim}(x, e_i) \geq \theta_{sim} \) — степень схожести превышает установленный порог;
- \( liveness(x) = 1 \) — лицо признано живым;
- \( access\_rules(i^*, checkpoint) = true \) — у сотрудника есть право прохода через данную проходную.

Порог \( \theta_{sim} \) определяется на этапе валидации исходя из целевых значений FAR и FRR.

**Связь с бизнес-целями.** Метрика FAR (False Acceptance Rate — доля ложных допусков) напрямую связана с уровнем безопасности. Метрика FRR (False Rejection Rate — доля ложных отказов) определяет удобство сотрудников и пропускную способность проходной. Метрика latency (задержка отклика) влияет на скорость прохода. Таким образом, качество ML-модели транслируется в измеримые бизнес-показатели.

### 2.2. Блок-схема решения

Решение выстраивается в два последовательных уровня: **бейзлайн** (baseline — базовая версия для проверки гипотезы) и **MVP** (minimum viable product — минимально жизнеспособная версия для пилота).

#### 2.2.1. Бейзлайн

Цель бейзлайна — оперативно проверить принципиальную работоспособность подхода и получить первые оценки метрик.

Состав бейзлайна:

1. Использование предобученной модели формирования эмбеддингов лиц (FaceNet, ArcFace, InsightFace) без дообучения.
2. Предобработка эталонных фотографий сотрудников: детекция лица, выравнивание, нормализация.
3. Расчёт эмбеддингов и их размещение в хранилище.
4. Обработка кадра с камеры: детекция лица, расчёт эмбеддинга, поиск ближайшего соседа по косинусной близости.
5. Применение порога схожести для принятия решения.
6. Запись события в журнал.

Ограничения бейзлайна: отсутствие модуля liveness, отсутствие реальной интеграции с турникетом, эмпирический подбор порога.

#### 2.2.2. Основной MVP

MVP расширяет бейзлайн следующими компонентами:

1. **Собственная или дообученная модель эмбеддингов.** Дообучение на данных предприятия (условия освещения, спецодежда, средства индивидуальной защиты) повышает точность распознавания.
2. **Модуль liveness.** Отдельная модель, различающая живое лицо и имитацию.
3. **Векторный индекс.** Специализированное хранилище (FAISS, Milvus, Qdrant) для быстрого поиска ближайших соседей среди ~5000 эмбеддингов.
4. **Интеграция с СКУД.** Передача управляющего сигнала турникету.
5. **Журналирование.** Фиксация всех событий прохода: время, проходная, камера, результат, степень уверенности.
6. **Ручной режим охраны.** Возможность вмешательства при низкой уверенности системы.
7. **Мониторинг.** Отслеживание качества, дрейфа данных, необходимости переобучения.

Последовательность обработки в MVP:

1. Сотрудник приближается к камере на проходной.
2. Камера фиксирует кадр.
3. Выполняется детекция лица.
4. Вычисляется эмбеддинг.
5. Осуществляется поиск по векторному индексу.
6. Проверяется liveness.
7. Проверяются права доступа.
8. Формируется управляющий сигнал для СКУД.
9. Событие записывается в журнал.

### 2.3. Этапы решения задачи

#### Этап 1. Подготовка данных

| Название данных | Наличие в компании | Источник | Требуемые роли | Качество проверено |
|---|---|---|---|---|
| HR-база сотрудников | Да | HR-система (1С) | HR, дата-инженер | Частично |
| Эталонные фотографии | Да | База пропусков | HR, дата-инженер | Нет |
| Дополнительные фотографии (разные ракурсы) | Нет | Съёмка на пилотной группе | HR, дата-аналитик, охрана | Нет |
| Видеозаписи с проходных | Частично | Архив камер | дата-инженер, охрана | Нет |
| Логи проходов | Да | СКУД | дата-инженер | Частично |
| Права доступа | Да | СКУД / HR | дата-инженер | Да |
| Датасет liveness (примеры имитаций) | Нет | Публичные датасеты и собственная съёмка | дата-аналитик | Нет |
| Разметка «свой / чужой» | Нет | Ручная разметка | дата-аналитик, охрана | Нет |

**Результат этапа:** витрина данных с эталонными фотографиями и эмбеддингами; отдельные наборы для валидации задачи идентификации и задачи liveness; документированный пайплайн подготовки данных.

**Риски этапа:** недостаточное количество качественных фотографий; устаревшие снимки; отсутствие согласий на обработку биометрических данных; дисбаланс выборки по полу, возрасту, национальности.

**Меры:** дополнительная съёмка на пилотной группе; обновление устаревших фотографий; юридическое оформление согласий; балансировка выборки.

---

#### Этап 2. Подготовка прогнозных моделей

**Бейзлайн:**
- применение готовой предобученной модели без дообучения;
- эмпирический подбор порога схожести;
- оценка FAR и FRR на отложенной выборке.

**MVP:**
- дообучение модели эмбеддингов на данных предприятия (ArcFace, AdaFace);
- обучение отдельной модели liveness;
- кросс-валидация по сотрудникам и по проходным.

**Формирование выборки:**
- обучающая часть — 70% сотрудников;
- валидационная — 15%;
- тестовая — 15%;
- разбиение выполняется **по сотрудникам**, а не по изображениям, что исключает утечку данных (data leakage) и завышение оценок качества.

**Целевая переменная:**
- для задачи идентификации — идентификатор сотрудника (или класс «чужой»);
- для задачи liveness — бинарный признак «живое / подделка».

**Метрики качества:**

| Метрика | Содержание | Целевое значение (MVP) | Связь с бизнесом |
|---|---|---|---|
| FAR | Доля ложных допусков | ≤ 0,001–0,01% | Безопасность |
| FRR | Доля ложных отказов | ≤ 1–2% | Пропускная способность |
| TAR@FAR=1e-4 | Доля верных допусков при строгом пороге | ≥ 95% | Баланс безопасности и удобства |
| EER | Точка равных ошибок | ≤ 1% | Общая оценка качества |
| Rank-1 | Доля случаев, когда верный сотрудник первый в ранжировании | ≥ 98% | Точность идентификации |
| APCER | Доля пропущенных имитаций | ≤ 0,1% | Защита от подделок |
| BPCER | Доля живых лиц, отвергнутых как подделка | ≤ 1% | Удобство |
| Latency | Задержка отклика | ≤ 2 сек | Пропускная способность |

**Результат этапа:** обученная модель эмбеддингов; обученная модель liveness; отчёт с метриками; обоснованный порог схожести.

**Риски:** переобучение на пилотной группе; снижение качества на отдельных категориях сотрудников; дрейф данных; попытки имитации.

**Меры:** кросс-валидация по сотрудникам; тестирование на отдельной группе; регулярная переоценка качества; отдельное тестирование на имитациях.

---

#### Этап 3. Интерпретация результатов модели

Для задач распознавания лиц полная интерпретируемость модели ограничена, однако применяются следующие подходы:
- анализ распределения значений схожести;
- построение ROC-кривых (кривых «ошибка — порог»);
- выявление групп сотрудников с повышенным FRR;
- анализ причин ошибок (освещение, очки, каска, ракурс).

**Результат этапа:** аналитический отчёт с перечнем причин ошибок и рекомендациями по их снижению.

---

#### Этап 4. Интеграция бизнес-правил

Формализуются и реализуются следующие правила:
- доступ разрешается только в пределах рабочей смены;
- доступ в определённые зоны — согласно правам сотрудника;
- при низкой уверенности модели — обязательная ручная проверка охраной;
- при повторных ложных отказах — уведомление администратора;
- при признаках имитации — сигнал охране.

**Результат этапа:** формализованный набор правил, реализованный в сервисе принятия решений.

---

#### Этап 5. Подготовка инференса модели

- Развёртывание инференса (inference — процесс применения обученной модели) на edge-устройстве (Jetson, Intel NUC) или локальном сервере.
- Настройка векторного индекса (FAISS, Milvus, Qdrant).
- Разработка API для взаимодействия со СКУД.
- Реализация fallback-режима (резервного сценария) при отказе системы.
- Логирование всех решений.

**Результат этапа:** работающий сервис инференса на пилотных проходных.

---

#### Этап 6. Настройка пороговых значений

- Подбор порога \( \theta_{sim} \) под целевые значения FAR и FRR.
- Возможность задания различных порогов для разных проходных и зон.
- Учёт времени суток и условий освещения.

**Результат этапа:** оптимальные пороговые значения для условий пилота.

---

#### Этап 7. Подготовка итогового отчёта

- Метрики, полученные в ходе пилота.
- Перечень инцидентов и их разбор.
- Обратная связь от охраны и сотрудников.
- Рекомендации по масштабированию.
- План закрытия технического долга.

**Результат этапа:** итоговый отчёт и решение о масштабировании системы.

## 3. Подготовка пилота

---

### 3.1. Способ оценки пилота

#### 3.1.1. Дизайн пилота

| Параметр | Значение |
|---|---|
| Количество проходных | 2 (высокая и средняя нагрузка) |
| Сотрудников в пилоте | 300–500 добровольцев из разных подразделений |
| Длительность | 4–6 недель |
| Режим | Параллельный: система + ручная проверка охраной |
| Уровень автоматизации | Рекомендательный: система предлагает, охрана подтверждает |
| Камеры | 1 камера на проходную |
| Вычислительный контур | Локальный: edge-устройство + локальный сервер |

#### 3.1.2. Схема проведения пилота

**Фаза 1. Подготовительная (1–2 недели):** регистрация добровольцев, сбор фото и согласий, настройка оборудования, калибровка камеры, тестовые прогоны без допуска.

**Фаза 2. Основная (2–3 недели):** система работает в рекомендательном режиме. Фиксируются расхождения в двух симметричных кейсах:
- система нашла сотрудника и предложила допуск, охрана отказала;
- система не нашла сотрудника или предложила отказ, охрана допустила вручную.

Собираются метрики FAR (False Acceptance Rate — доля ложных допусков), FRR (False Rejection Rate — доля ложных отказов), latency (задержка отклика), доля ручных вмешательств. Проводятся контролируемые тесты на имитацию (фото, видео, маска).

**Фаза 3. Аналитическая (1 неделя):** расчёт метрик, разбор инцидентов, опрос охраны и сотрудников, формирование отчёта.

#### 3.1.3. Способ оценки

Оценка строится на трёх уровнях:

1. **Технические метрики (автоматически):**
   - FAR (False Acceptance Rate — доля ложных допусков);
   - FRR (False Rejection Rate — доля ложных отказов);
   - TAR@FAR (True Acceptance Rate at fixed FAR — доля верных допусков при заданном уровне ложных допусков);
   - EER (Equal Error Rate — точка равных ошибок);
   - APCER (Attack Presentation Classification Error Rate — доля пропущенных имитаций);
   - BPCER (Bona Fide Presentation Classification Error Rate — доля живых лиц, ошибочно отвергнутых как подделка);
   - latency, доля ручных вмешательств, доля отказов оборудования.

2. **Операционные метрики (собирает охрана):** среднее время прохода, очереди и задержки, ложные тревоги, спорные ситуации.

3. **Качественные оценки (опросы):** удовлетворённость охраны и сотрудников, удобство интерфейса, доверие к системе.

#### 3.1.4. Контрольная группа

- **Тестовая группа** — сотрудники на пилотных проходных с системой распознавания.
- **Контрольная группа** — сотрудники на обычных проходных с ручной проверкой.

Сравнение по: времени прохода, количеству инцидентов, нагрузке на охрану, субъективной оценке удобства.

---

### 3.2. Что считаем успешным пилотом

#### 3.2.1. Формализованные критерии успеха

| Критерий | Целевое значение | Способ измерения |
|---|---|---|
| FAR | ≤ 0,01% | Автоматически |
| FRR | ≤ 2% | Автоматически |
| TAR@FAR=1e-4 | ≥ 95% | Автоматически |
| APCER | ≤ 0,1% | Контролируемые тесты |
| BPCER | ≤ 1% | Автоматически |
| Latency | ≤ 2 сек | Автоматически |
| Доля ручных вмешательств | ≤ 10% | Логи охраны |
| Доступность системы | ≥ 99% в рабочее время | Мониторинг |
| Удовлетворённость охраны / сотрудников | ≥ 4 / ≥ 3,5 из 5 | Опрос |

#### 3.2.2. Качественные критерии успеха

- отсутствие критичных инцидентов безопасности;
- отсутствие массовых жалоб сотрудников;
- готовность охраны продолжать работу с системой;
- готовность руководства рассматривать масштабирование;
- отсутствие нарушений законодательства о персональных данных.

#### 3.2.3. Критерии остановки пилота

- превышение FAR выше допустимого уровня;
- системная уязвимость к имитации;
- массовые ложные отказы, создающие очереди;
- технические сбои, влияющие на безопасность;
- нарушения в обработке биометрических данных.

#### 3.2.4. Возможные пути развития

1. **Масштабирование** — перенос на все 10 проходных.
2. **Поэтапное масштабирование** — сначала 3–4 проходные, затем остальные.
3. **Расширение функциональности** — замена пропусков биометрией, интеграция с учётом рабочего времени.
4. **Доработка** — устранение недостатков и повторный пилот.
5. **Ограниченное внедрение** — только отдельные проходные или зоны.
6. **Отказ** — если эффект не подтверждён.

### 3.3. Подготовка пилота

#### 3.3.1. Вычислительные ресурсы

| Компонент | Назначение | Пример конфигурации |
|---|---|---|
| Edge-устройство | Детекция, эмбеддинг, liveness | NVIDIA Jetson Orin / Intel NUC с GPU |
| Локальный сервер | Векторный индекс, API, журнал | 1 сервер с GPU (A10 / T4) |
| Камера | Съёмка лица | 1 камера на проходную (Full HD, ИК) |
| Сеть | Передача данных | Локальная сеть с изоляцией |
| Хранилище | Фото, эмбеддинги, логи | Объектное хранилище + БД |

#### 3.3.2. Оценка вычислительной сложности

**Инференс:** детекция ~30–50 мс, эмбеддинг ~50–100 мс, liveness ~30–50 мс, поиск по индексу ~1–5 мс, итого ~150–250 мс без учёта сети.

**Пропускная способность:** одна проходная — 10–15 человек/мин, две — до 30 человек/мин.

**Обучение:** дообучение эмбеддингов — 1 GPU, 6–12 часов; liveness — 1 GPU, 4–8 часов; подготовка данных — CPU-кластер.

#### 3.3.3. Ограничения пилота

- пилот дополняет, а не заменяет текущий процесс;
- система не принимает финальное решение без подтверждения охраны;
- биометрия обрабатывается только в защищённом контуре;
- участие добровольное, с оформлением согласий;
- не охватываются сценарии: проход группы по одному подтверждённому лицу, мультикамерное сопровождение, зоны вне пилотных проходных.

#### 3.3.4. Регламент взаимодействия

**Охрана:** видит решение и уверенность; при высокой уверенности подтверждает, при низкой — решает вручную; при имитации — тревога; спорные ситуации фиксируются.

**Сотрудники:** добровольное участие, возможность отказа, инструкция, канал обратной связи.

**Администратор:** ежедневный мониторинг метрик, еженедельный отчёт, оперативная реакция на инциденты.

## 4. Внедрение для production

---

### 4.1. Архитектура решения

**Принцип:** распределённая обработка — edge-уровень на проходной + central-уровень на локальном сервере предприятия. Это обеспечивает низкую задержку, отказоустойчивость и защиту биометрии.

**Компоненты:**

| Уровень | Компонент | Назначение |
|---|---|---|
| Edge | Камера | Съёмка лица |
| Edge | Edge-устройство | Детекция, эмбеддинг, liveness, локальный кэш |
| Central | Локальный сервер | Векторный индекс, API, принятие решений, журнал |
| Central | Векторная БД | Эмбеддинги сотрудников, поиск ближайших соседей |
| Central | Реляционная БД | Метаданные, права доступа, журнал событий |
| Central | Объектное хранилище | Фотографии, архив |
| Central | Сервис интеграции с СКУД | Управляющий сигнал турникету |
| Central | Сервис интеграции с HR | Синхронизация сотрудников и прав |
| Central | Сервис мониторинга | Метрики, оповещения, дрейф |
| Central | Административная панель | Управление, журналы, пороги |

**Последовательность обработки:** кадр → детекция → эмбеддинг → поиск по индексу → liveness → проверка прав → решение → сигнал в СКУД → журнал → метрики.

**Ключевые API:** `POST /recognize`, `POST /liveness`, `GET /access/check`, `POST /access/log`, `GET /monitoring/metrics`, `POST /admin/threshold`.

**Распределённость обусловлена:** разнородными источниками данных, разными требованиями к задержке, разными объёмами данных, требованиями безопасности и отказоустойчивости.

---

### 4.2. Инфраструктура и масштабируемость

**Выбор:** on-premise (на территории предприятия) с edge-контуром на проходных. Публичные облака для биометрии исключены.

**Причины:** требования 152-ФЗ, низкая задержка, доступность, безопасность, предсказуемая стоимость владения.

**Плюсы:** полный контроль, соответствие 152-ФЗ, низкая задержка, независимость, предсказуемые затраты.  
**Минусы:** высокий CAPEX, собственная поддержка, ограниченная эластичность, необходимость резервирования.

**Альтернативы и отказ:** публичное облако (юридические риски), российское облако (согласования, задержка), гибрид (усложнение), полностью edge (нет централизации), полностью central (задержка, риск при обрыве связи).

**Масштабируемость:**
- по проходным: 2 → 3–4 → 10;
- по сотрудникам: 5000 → 10 000+;
- по событиям: до 10 000/день, пики в 3–4 раза выше.

**Способы:** вертикальное (мощнее сервер), горизонтальное (добавление серверов), шардирование индекса, кэш на edge.

---

### 4.3. Требования к работе системы

**SLA:** доступность ≥ 99,9% в рабочее время, реакция на инцидент ≤ 15 мин, восстановление ≤ 1 ч, плановое обслуживание 1 раз/мес, поддержка 8×5 + on-call, ежедневный бэкап.

**RPS:** средняя нагрузка 0,1–0,2 RPS, пиковая 1–2 RPS, максимум 5 RPS. Пропускная способность одной проходной — 10–15 чел/мин, всех 10 — 100–150 чел/мин.

**Latency:** целевая ≤ 2 сек для 95% событий, ≤ 3 сек для 99%. Разбивка: захват кадра ≤50 мс, детекция ≤50 мс, эмбеддинг ≤100 мс, liveness ≤50 мс, передача ≤20 мс, поиск ≤10 мс, проверка прав ≤20 мс, решение ≤10 мс, сигнал ≤20 мс. Итого ≤330 мс без очереди.

**Дополнительно:** холодный старт ≤5 мин, переключение на резерв ≤30 сек, автономная работа edge ≥15 мин, хранение логов ≥12 мес, фото ≥5 лет, сеть ≥100 Мбит/с, ИБП ≥30 мин.

**Режимы:** штатный, рекомендательный (пилот), автономный, ручной.

---

### 4.4. Безопасность системы

**Уязвимости:** физические (кража edge, подмена камеры), сетевые (перехват, доступ), прикладные (атаки на API, компрометация панели), модельные (adversarial, обход liveness), данные (утечка, доступ к журналам), человеческие (саботаж, социальная инженерия).

**Меры по уровням:**
- физический: защищённые корпуса, датчики вскрытия, видеонаблюдение, контроль доступа в серверную, ИБП;
- сетевой: изоляция от корпоративной сети и интернета, TLS 1.3, VPN, VLAN, межсетевой экран, мониторинг трафика;
- прикладной: mTLS, токены, валидация, разграничение прав, логирование, обновления, изоляция моделей;
- модельный: тесты на adversarial, обучение liveness на имитациях, мониторинг аномалий, переобучение, ручная проверка при подозрении;
- данные: шифрование AES-256, разделение хранилищ, бэкап с шифрованием, аудит, удаление по срокам;
- человеческий: обучение, 2FA для админов, разделение обязанностей, аудит, регламент.

**Роли:** охрана, оператор, администратор, аудитор, СБ, ИТ. Принцип минимальных привилегий.

**Мониторинг:** доступ к API, паттерны проходов, изменения прав, попытки обхода liveness, доступ к биометрии, состояние edge, целостность моделей.

**Реагирование:** обход liveness → сигнал охране; компрометация edge → отключение и замена; утечка → расследование; сбой камеры → ручной режим; саботаж → внутреннее расследование.

---

### 4.5. Безопасность данных

**Принципы:** биометрия — специальная категория персональных данных, обработка по 152-ФЗ.

**Соответствие 152-ФЗ:** письменное согласие, целевое использование, минимизация, сроки хранения (фото 5 лет, эмбеддинги до отзыва, логи 12 мес), право на удаление, уведомление РКН, защита, хранение в РФ, отсутствие трансграничной передачи.

**Классификация и хранение:**

| Данные | Где хранится | Срок хранения | Шифрование |
|---|---|---|---|
| Эталонные фото | Объектное хранилище | 5 лет / до отзыва | AES-256 |
| Эмбеддинги | Векторная БД | До отзыва согласия | AES-256 |
| Видео с КПП | Объектное хранилище | 30 дней | AES-256 |
| Метаданные | Реляционная БД | Договор + 5 лет | AES-256 |
| Журналы событий | Реляционная БД + архив | 12 месяцев | AES-256 |
| Права доступа | Реляционная БД | Актуальность + 3 года | AES-256 |
| Логи администратора | Реляционная БД | 3 года | AES-256 |
| Метрики | БД мониторинга | 12 месяцев | Нет |

**Меры:** шифрование при хранении и передаче, разделение хранилищ, бэкап, контроль целостности, физическая защита, минимальные привилегии, аудит, анонимизация, автоудаление.

**Права субъектов:** информация, доступ, уточнение, отзыв согласия, удаление (30 дней), обжалование. Обращения рассматриваются в течение 30 дней.

**Ответственные:** оператор (предприятие), ответственный за ПДн, СБ, ИТ, юрист, дата-инженер.

**Риски:** утечка, несанкционированный доступ, нарушение сроков, обработка без согласия, трансграничная передача, инцидент. Меры: шифрование, разграничение, автоудаление, проверка согласий, изоляция, план реагирования.

### 4.7. Точки интеграции

**Принципы:** изоляция, минимизация, асинхронность где возможно, идемпотентность, логирование.

**Карта интеграций:**

| Система | Направление | Назначение | Частота |
|---|---|---|---|
| HR | Вход | Сотрудники, подразделения | Ежедневно |
| HR | Выход | Уведомления об изменениях | По событию |
| СКУД | Выход | Сигнал турникету | По событию |
| СКУД | Вход | Права, зоны, смены | Ежедневно |
| Учёт времени | Выход | События прохода | По событию |
| Видеонаблюдение | Вход | Видеопоток | Потоково |
| Мониторинг | Выход | Метрики и алерты | Постоянно |
| Бэкап | Выход | Резервные копии | Ежедневно |
| Админ-панель | Двусторонне | Управление и просмотр | По запросу |

**Ключевые API:** HR — `GET /hr/employees`, `POST /hr/notify`; СКУД — `POST /access/decision`, `GET /access/rules`, `POST /access/log`; учёт времени — `POST /timetracking/event`; мониторинг — `POST /monitoring/metrics`, `POST /monitoring/alerts`; админ — `GET /admin/employees`, `POST /admin/employees/{id}/photo`, `GET /admin/events`, `POST /admin/threshold`, `GET /admin/health`.

**Протоколы:** HTTPS/TLS 1.3, gRPC, REST, MQTT, WebSocket, SFTP. Форматы: JSON, Protobuf, CSV, JPEG/PNG, MP4/H.264.

**Обработка ошибок:** при недоступности HR — последняя синхронизация; СКУД — автономный режим edge; мониторинга — буферизация; ошибки API — 3 попытки с backoff 1/5/30 сек; невалидные данные — отклонение и лог; таймаут — fallback.

**Безопасность:** mTLS, API-ключи, валидация, rate limiting, логирование, VLAN, allow-list.
